# Agent 工作区模板理解通用 Skill

这份 skill 的目标不是指导 agent 的执行顺序，而是帮助 agent 读懂当前 workspace 模板为什么能运行、依赖哪些契约、哪些位置可以写实、哪些位置必须严格兼容已有骨架。

图解释、上下游拓扑、协作顺序，默认已经由已有模板、运行时、flow、build plan 或上游任务决定；不要在本 skill 中自行补做这些决定。

## 核心定位

使用这份 skill 时，优先把当前任务理解为：

- 识别模板的运行闭环，而不是只补齐文件。
- 识别哪些文件是真正的运行时依赖，哪些只是业务内容承载位。
- 识别哪些字段会被 runtime / flow / parser 真实消费。
- 基于现有模板生成兼容实现，而不是生成“结构完整但运行时不认”的占位代码。

如果一个 workspace 中已经存在基础骨架，这份 skill 的首要作用是帮助 agent 顺着骨架工作，而不是重写骨架、复制另一套基础设施，或把抽象框架经验硬套到当前模板上。

## 输入前提

在开始修改前，默认上游任务已经提供或隐含提供了以下信息：

- workspace 路径
- 当前 in-scope 的 agent / prompt / workflow / runtime 文件
- 工作区已有模板代码与目录结构
- 已有运行入口、配置文件与 build plan

如果其中某项缺失，不要自己从图里推断。只使用明确的任务文本、已生成的工作区文件与当前模板中真实存在的契约。

## 先识别当前修改所依赖的最小契约

这份 skill 不要求先做 multi-agent 意义上的全量分析；那部分应由对应的任务型 skill（例如 `multi_agent_skill`）负责。

在 common 层，只需要识别“当前 in-scope 文件为了保持兼容，最少必须知道什么”。通常包括：

- 当前修改会挂到哪个运行入口、runtime 模块或调用链上。
- 当前文件依赖哪些命名、目录、基类、配置字段或 loader 约定。
- 当前文件产出的字段、返回值或文本格式，会被谁真实消费。
- 当前文件提到的 model、prompt、flow、build plan 约束，哪些是真实存在的，哪些只是上层协作语义。

如果任务只涉及单个 agent、prompt、tool 或配置文件，不要为了“先看全局”而额外扩展到整个 workspace。
只有当当前修改无法在局部契约中解释清楚时，才继续向外追踪到 runtime、flow 或更大范围的模板闭环。

## 硬契约与可变区

完成模板理解时，优先区分“硬契约”和“可变区”。

### 硬契约

以下内容通常视为运行闭环的一部分，除非明确发现骨架本身有错，否则不要随意改写语义：

- 目录结构与文件命名约定。
- 基类、协议、接口、抽象方法与必填字段。
- agent 的最小合法入口，例如 `run()`、`invoke()`、`execute()` 等当前框架真实要求的方法。
- runtime 对 agent、flow 的发现与装配方式。
- prompt loader、config、model adapter 的依赖连接方式。
- flow parser / runtime 真正消费的结构化字段名、停止条件与 handoff 字段。
- 空值约定、保底值、默认配置、环境变量命名与缓存行为。
- 不能删除仍被当前 runtime、flow、parser 或注册链路依赖的导入、基类引用、注册语句与桥接代码；如果某行看起来像样板代码，也必须先确认它没有被真实调用后才能改。

### 可变区

以下内容通常应该写得更贴近当前项目与角色，而不是保持模板腔：

- prompt 中的身份、职责、输入理解与输出质量标准。
- agent 的任务边界、失败处理、澄清策略与最终回答要求。
- 业务领域术语、交付物定义、验收视角与角色差异。
- 在不破坏硬契约前提下，对 prompt、schema 文案、说明文本的具体化与去模板化。

要避免两类错误：

- 把硬契约当成文风问题，随意改掉，导致 runtime 失配。
- 把可变区也当成骨架复制粘贴，导致输出虽然完整但没有真实任务感。

## 模型、配置与环境加载

在大多数模板里，agent 本身并不真正决定模型行为；通常是 `Config/*`、`Model/*` 与 runtime 一起决定：

- 默认模型名称、base URL、温度、max tokens、是否流式，通常由配置文件管理。
- API key 往往不是硬编码在 agent 中，而是通过 `.env` 或环境变量名间接加载。
- 配置层可能有缓存语义，不能默认每次调用都会重新读取。
- model adapter 可能同时承担流式输出、stdout/stderr 编码、系统 prompt 注入等职责。

因此，不要把本应属于配置层或 model 层的行为错误地下沉到单个 agent 文件中。除非当前框架就是这样设计，否则不要在 agent 里重写环境变量加载、流式策略或编码兜底逻辑。

## Prompt / Role Contract

在大多数模板中，prompt 不是附属文案，而是运行契约的一部分。补全 prompt 时，至少要确认：

- 当前角色是谁、职责边界是什么。
- 当前 agent 接收什么输入、依赖哪些上下文。
- 当前 agent 必须产出什么结果，结果会不会被 runtime 或 flow 继续消费。
- 当前 agent 是否需要 handoff，如果需要，handoff 字段是否真的被现有 runtime / flow 消费。
- 当前 agent 是否真的具备工具调用能力；如果具备，只说明你可以进行工具的调用，不要在业务 prompt 中写死具体工具调用格式、参数示例或臆造工具名。
- 如果当前 runtime 没有给该 agent 注入工具，prompt 应明确其不能调用工具，只能基于输入上下文和已知信息回答，并在信息不足时说明不确定性或请求补充信息。
- 当前 agent 的停止条件、失败处理方式与不确定时的处理策略。
- 当前 agent 的最终输出质量标准，而不是只满足字段齐全。

只有在工作区契约明确要求结构化字段时，才固定输出 schema。不要为了“看起来整齐”强行加入对 runtime 无意义、对用户也无价值的字段。

## Agent 代码补全原则

在多数模板里，`Agent/*.py` 更像最薄的运行适配层，而不是 orchestration 主战场。补全代码时优先遵守：

- 除非生成骨架本身有问题，否则保留原有文件结构。
- `__init__()`、config、prompt loader、model 连接方式要与生成骨架保持一致。
- 实现当前框架要求的最小合法 entrypoint，而不是预设所有框架都应该长得一样。
- 返回或产出当前 runtime / flow / parser 约定的内容形状。
- 不要把 orchestration 逻辑或整套新协议硬塞进 agent 代码，除非当前框架本身就是代码驱动协作。
- 如果某个节点会被当前框架发现、实例化或执行，就需要满足该阶段所需的完整契约，不要保留为半完成状态。

## 明确不要做的事

- 不要凭空补做图推理、上下游语义推断、额外 flow 文件或额外 context 文件。
- 不要发明新的下游 agent，只能使用任务文本或现有工作区中已经出现的名称。
- 不要给现有基类、接口或 skeleton 增加不受支持的构造参数。
- 不要把某一种 agent 框架的默认写法直接套用到另一种框架上。
- 不要伪造真实 API key、Token 或任何密钥。
- 不要把“模板更完整”误当成“工作区已可运行”。

## 与其他 skill 的边界

这份 skill 只负责帮助 agent 理解模板闭环与契约边界。

- 如果任务重点是单个 agent 的角色补全、prompt 写实化与最小入口补齐，可在此基础上叠加 single-agent skill。
- 如果任务重点是多节点协作、flow、runtime 闭环、批量对齐与统一验收，可在此基础上叠加 multi-agent skill。
- 如果用户明确在问系统设计、图结构或协作顺序，不要由本 skill 代替对应的 flow / orchestration 分析。
